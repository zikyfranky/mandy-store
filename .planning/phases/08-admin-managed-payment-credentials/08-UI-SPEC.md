# Phase 8 — UI Design Contract: Admin-Managed Payment Credentials

> Visual and interaction contract for the credential-management surface added to the existing
> `/admin/settings` page. Generated by gsd-ui-researcher in autonomous mode (no user prompts — all
> values are pre-populated from `08-CONTEXT.md`'s locked decisions, `08-RESEARCH.md`'s field
> manifest, or a direct read of the existing `05-UI-SPEC.md` admin design system, which this
> document extends rather than replaces). Verified by gsd-ui-checker.

**Scope discipline:** This spec does NOT re-derive spacing/typography/color tokens from scratch —
it inherits them verbatim from `05-UI-SPEC.md` (Phase 5, Admin Panel). Only the new
credential-card surface, its states, and its copy are specified here. Any token not restated below
is unchanged from Phase 5.

## Surfaces

### Surface 6 (extended): Settings — Payment methods → Gateway credential cards

This extends `05-UI-SPEC.md` Surface 6. The existing "Payment methods" section card and its three
`PaymentToggleRow` rows (Stripe, PayPal, Bank transfer) are unchanged in position and behavior.
**All 8 gateways** get a credential-management disclosure — including the 5 NG gateways
(Paystack/Flutterwave/Interswitch/GTPay/Remita) that Phase 5 (D-11/U-12) intentionally excluded
from the toggle rows. Credential management is a distinct concern from the enable/disable toggle
(D-04's scope is credentials, not toggling), so this phase adds a **second section card**, "Gateway
credentials," below the existing "Payment methods" card — it does not retrofit toggle rows onto the
5 NG gateways (that stays out of scope per Phase 5's locked exclusion).

**Page structure (top to bottom):**
1. "Settings" heading (unchanged, 24px)
2. Existing "Payment methods" section card (unchanged: Stripe/PayPal/Bank transfer toggles)
3. **NEW** "Gateway credentials" section card (`rounded-2xl bg-surface border border-border p-6`):
   - One-line security note (Copywriting Contract) directly under the section heading, `text-sm text-muted`, `LockClosedIcon` prefix (new Heroicon, matches the existing icon inline-SVG style)
   - 8 rows, one per gateway, in this order: **Stripe, PayPal, Bank transfer, Paystack,
     Flutterwave, Interswitch, GTPay, Remita** — Stripe/PayPal/Bank transfer first (mirrors the
     toggle-row order above them, visual continuity), then the 5 NG gateways grouped together in
     their existing codebase order (matches `FIELD_MANIFEST` order in 08-RESEARCH.md)
   - Each row = a **disclosure** (collapsed by default for ALL gateways on first page load,
     regardless of configured state — do not auto-expand configured gateways, to avoid a wall of
     open forms on load)

**Collapsed row anatomy** (`flex items-center justify-between py-4 border-b border-border
last:border-0`, mirrors `PaymentToggleRow`'s row rhythm exactly):
- Left: gateway icon (reuse the exact icon already used for Stripe/PayPal/Bank transfer in
  `settings/page.tsx`; for the 5 NG gateways, reuse whatever icon set `PaymentMethodSelector`
  already defines for them on the storefront side — do not invent new icons) + gateway label (14px
  semibold) + status dot + status label (Copywriting Contract: "Not configured" / "Incomplete" /
  "Configured")
- Right: disclosure trigger button — text link style (`text-sm font-semibold text-brand
  hover:text-brand-strong`), the trigger label itself IS the status-dependent copy ("Configure
  credentials" / "Finish setup" / "Manage credentials"), with a `ChevronDownIcon` that rotates 180°
  when expanded (exact pattern from `CheckoutOrderSummary`'s `aria-expanded` mobile-summary
  disclosure — `aria-expanded={expanded} aria-controls="{provider}-credentials-panel"`)

**Expanded panel anatomy** (renders below the row, `bg-background border-t border-border p-4
rounded-b-xl space-y-4`, `id="{provider}-credentials-panel"`):
- One field group per manifest entry for that provider (08-RESEARCH.md Field Manifest table — the
  28-field breakdown across 8 gateways), each field rendered per the **Field Rendering Contract**
  below, in manifest order (secret fields and public fields interleaved in their natural order, not
  segregated into two sub-lists — e.g. Stripe renders `secret_key`, then `webhook_secret`, then
  `publishable_key`, matching the manifest table row order)
- Footer row inside the panel (`flex items-center justify-between gap-3 flex-wrap pt-2 border-t
  border-border`):
  - Left: Test-connection affordance (button + result badge for Stripe/Paystack/Flutterwave, OR
    the static "Saved — not verifiable" pill for Interswitch/GTPay/Remita, OR nothing for
    PayPal/Bank transfer — see Test-Connection Applicability below)
  - Right: "Save {gateway} credentials" button (brand, filled)
- Save-error banner (if present) renders ABOVE the field groups, inside the panel, full-width —
  matches Phase 5's product-save-failure banner exactly (`bg-red-50 border-red-200
  ExclamationCircleIcon`)

**Test-Connection Applicability** (D-06):
| Gateway | Affordance |
|---------|-----------|
| Stripe | "Test connection" button → `balance.retrieve()` |
| Paystack | "Test connection" button → authenticated `GET /balance` |
| Flutterwave | "Test connection" button → authenticated `GET /v3/balances` |
| Interswitch, GTPay, Remita | Static "Saved — not verifiable" pill, no button |
| PayPal | No test-connection affordance and no "not verifiable" pill — PayPal stays out of D-06's scope entirely (deferred/OFF per D-09); render nothing in the footer's left slot for this row |
| Bank transfer | No test-connection affordance — there is no external API to ping for a bank-transfer method; render nothing in the footer's left slot |

**Test-connection mechanism** (per 08-RESEARCH.md Open Question #1, resolved here for the UI
contract): the button tests the **currently-typed form values** (unsaved), not the persisted DB
value, when the admin has entered anything since opening the panel. If the admin has made no edits
(all secret fields still show masked "Configured" state), the button tests the **already-saved**
value. This is a single "Test connection" affordance whose behavior is contextual, not two separate
buttons — the button's disabled/enabled state and label do not change based on this; only the
value it sends to the test action changes.

### Field Rendering Contract (the core of this phase's UI)

**Secret field (`is_secret: true`) — e.g. `secret_key`, `webhook_secret`, `mac_key`, `hash_key`,
`api_key`, `client_secret`, `webhook_hash`:**

| State | Rendering |
|-------|-----------|
| Unconfigured | Empty `<input type="password" autoComplete="off" />`, styled via `inputClass(hasError)`, placeholder "Not set", label above (14px semibold), helper text below (14px regular, muted): "This value is never displayed once saved." |
| Configured | Input is **not rendered as an editable field**. Instead: a read-only display row showing a fixed-length mask `••••••••` (`font-mono text-sm text-muted`, always the same visual length regardless of actual secret length — never leak length) + "Last updated {relative date} by {email}" (12px caption) + a "Replace" button (`text-sm font-semibold text-brand`, `aria-label="Replace {field label}"`) |
| Replace clicked | The masked display swaps for an empty, auto-focused `type="password"` input (same styling as Unconfigured state) + a "Cancel" link beside it that reverts to the masked display without clearing the stored value or submitting anything |
| Empty submit (field left masked/unedited) | On save, this field is simply omitted from the submitted payload for that field name — the Server Action's contract (08-RESEARCH.md D-05 pattern) treats "field absent from submission" as "leave unchanged." The UI must not submit an empty string for an untouched masked field. |

**Public field (`is_secret: false`) — e.g. `publishable_key`, `public_key`, `merchant_code`,
`merchant_id`, `product_id`, `pay_item_id`, `service_type_id`, `mode`, and all `*_url`/`*_base`
endpoint fields:**

| State | Rendering |
|-------|-----------|
| Any state | Normal `<input type="text" />` (or `type="url"` for the `*_url`/`*_base` fields, enabling native URL validation), styled via `inputClass(hasError)`, **pre-filled with the current value** if one is resolved (DB or env fallback — the read path already returns public values per D-05/08-RESEARCH.md), label above, optional helper text (e.g. the "Optional — leave blank to use the default…" copy for Interswitch/GTPay endpoint fields) |

**Absolute rule (security-in-UI, restated from CONTEXT D-04/RESEARCH Security Domain):** the
rendered HTML/props for a `is_secret: true` field NEVER contain the decrypted or stored value —
only a presence boolean, an `updated_at` timestamp, and an `updated_by` string cross from server to
client for secret fields. The masked `••••••••` string is a client-side literal, not derived from
any server value. This must hold even in the "Replace" state — the newly-typed value stays in local
component state only until form submission; it is never round-tripped through a prop from the
server.

## Accessibility Contracts

Inherited verbatim from `05-UI-SPEC.md`, restated/extended for this surface's new controls:

- **Disclosure triggers:** `aria-expanded={expanded}` + `aria-controls="{provider}-credentials-panel"` on the trigger button; the panel itself has `id="{provider}-credentials-panel"` and is only rendered in the DOM (or `hidden` toggled) when expanded — matches `CheckoutOrderSummary`'s existing mobile-summary disclosure pattern exactly, no new pattern invented.
- **Focus management on disclosure open:** when a row expands, move focus to the panel's first focusable field (the first input) — this is new interaction behavior for this codebase (no prior disclosure moved focus), added because these are data-entry forms, not read-only summaries like the existing `CheckoutOrderSummary` disclosure. On collapse (or Cancel-from-Replace), return focus to the trigger button that caused the collapse.
- **Password inputs:** every secret-field input uses `type="password"` and `autoComplete="off"` (never `autoComplete="current-password"`/`"new-password"` — these are API credentials, not user account passwords, and browser password-manager prompts would be actively unhelpful/confusing here). Each has a properly associated `<label htmlFor>` — no placeholder-as-label anti-pattern.
- **"Replace" control:** `aria-label="Replace {field label}"` on the button (the visible text "Replace" alone is ambiguous out of context for screen-reader users navigating by button list across 28 fields); once clicked, the newly-shown input receives focus automatically (`autoFocus` or a `ref.focus()` effect, consistent with the "focus management" rule above).
- **Masked value display:** the `••••••••` text is decorative in the sense that its exact character count carries no information — mark it `aria-hidden="true"` is NOT appropriate (the "Configured" state must be announced), instead render the accessible name via a visually-hidden sibling or a single combined `aria-label="{field label}: configured, last updated {date}"` on the container so screen readers get one clean announcement rather than reading out 8 bullet characters.
- **Status dots (gray/amber/green on collapsed rows):** never color-only — always paired with the text label ("Not configured"/"Incomplete"/"Configured") in the DOM, matching Phase 5's status-badge rule.
- **Test-connection result badges:** never color-only — icon + text label always present ("Connected"/"Test failed"), matching the Order Status Badge convention from Phase 5.
- **Save/Test buttons during pending state:** `aria-disabled` + `disabled`, exactly as `CheckoutForm`'s submit button and `ProductForm`'s save button already do.
- **Minimum touch target 44×44px** for the "Replace" button and the disclosure chevron control, even though this is a desktop-first admin surface (Phase 5's D-01/SC rule: must not break on mobile/tablet).
- **Focus rings:** `focus-visible:ring-2 focus-visible:ring-brand focus-visible:ring-offset-2` on every new interactive element (disclosure trigger, Replace button, Cancel link, Save button, Test connection button, all inputs) — zero exceptions, matching the house rule already established.
- **Color contrast:** the new zinc "not verifiable" pill and green "Connected" pill reuse Tailwind 50/700 (light) and 500/10-dark/300 (dark) pairings already verified AA-compliant elsewhere in Phase 5 — no new untested color pairing is introduced.

## Security-in-UI Contract (restated for the checker/executor)

This is not a visual rule but a hard design-contract boundary the checker must verify against the
implementation, per D-04/D-05 and 08-RESEARCH.md's Security Domain:

- The Settings Server Component's data-fetching for this surface returns, per field: `{ field, isSecret, isConfigured: boolean, updatedAt?: string, updatedBy?: string, publicValue?: string }`. For `isSecret: true` fields, `publicValue` is always `undefined` in the props/serialized payload sent to the client — never populate it, even with a truncated/partial value.
- No client component in this surface ever receives, stores in state, or logs the decrypted secret value — client state for a secret field only ever holds what the admin is actively typing in a Replace flow (never pre-populated from the server).
- The "Test connection" action's request body may include a freshly-typed secret value (to test before saving, per the resolved Open Question #1) — this travels client→server as a form submission to a Server Action (already the established secure channel, same as `saveGatewayCredentials`), never via a GET request, query string, or any code path that could land it in browser history, referrer headers, or client-side logs.
- Nothing on this surface introduces a new client-side fetch to any endpoint that could return a secret — all reads are Server Component props computed server-side (mirrors the existing `credentialsPresent` boolean pattern in `settings/page.tsx` verbatim, just extended to per-field granularity and all 8 gateways instead of 3).
