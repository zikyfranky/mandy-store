<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser form -> register/login/verifyEmail Server Action | untrusted user input; reachable via direct POST |
| verification token in email link -> verifyEmail | token is a bearer secret |
| env (ADMIN_EMAILS, SEED_ADMIN_PASSWORD) -> seed/register | privilege-granting config |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-10 | Tampering | registration input | mitigate | zod validation server-side on all fields before any DB write (ASVS V5) |
| T-01-11 | Spoofing | login enumeration | mitigate | login returns a single generic `{ error: "Invalid credentials" }` regardless of bad-user vs bad-password |
| T-01-12 | Tampering | verification token | mitigate | token is `crypto.randomUUID()` (high entropy), expires in 24h, single-use (deleted after success or expiry) — RESEARCH Pitfall 6 |
| T-01-13 | Elevation of Privilege | admin auto-promote | mitigate | role derived only from server-only `ADMIN_EMAILS` allowlist; never from form input (D-10, RESEARCH Pitfall 8) |
| T-01-14 | Information Disclosure | password storage | mitigate | argon2id hashing in both register and seed; plaintext never persisted |
| T-01-15 | Repudiation | brute-force on login | accept | login rate-limiting explicitly deferred (Claude's Discretion / CONTEXT deferred); argon2id slow-by-design partially mitigates; revisit in a hardening phase |
</threat_model>
