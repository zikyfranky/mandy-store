# Phase 7.1: Additional NG Gateways (fast-follow) - Research

**Researched:** 2026-07-05
**Domain:** NGN redirect-native payment gateways (Interswitch WebPay, GTPay, Remita) as new adapters against the Phase 7 `GatewayAdapter` interface
**Confidence:** HIGH (codebase seam + Interswitch/GTPay hash schemes) / MEDIUM (Remita JSONP response shape, per-merchant webhook availability)

## Summary

Phase 7.1 adds three **redirect-native** direct-integration gateways — Interswitch WebPay, GTPay, and Remita — as new `GatewayAdapter` implementations. Opay (PAY-07) and Palmpay (PAY-08) are **not built** (satisfied-via-channel through the Phase 7 aggregator popups, D-11). Unlike Phase 7's Paystack/Flutterwave inline popups, all three of these gateways use a **full-page HTTP POST/redirect to a hosted checkout page**, then return to a merchant callback URL. This is the exact case D-13/D-14 relaxed "never leaves the site" for.

The good news: the Phase 7 machinery generalizes almost perfectly. `buildOrderContext()`, `confirmOrderPaid()`, the `processed_webhook_events` idempotency guard, the `orders.gatewayProvider`/`orders.gatewayReference` columns, `getOrderByGatewayReference()`, the toggle system, and the status-polling fallback route are all reusable **verbatim**. The net-new work is: (1) three raw-`fetch` adapters with SHA-512 hash computation and requery/verify endpoints, (2) redirect init actions returning the D-16 `{mode:"redirect", url}` union, (3) per-gateway GET callback routes that run `verifyTransaction → confirmOrderPaid → redirect to /order/[token]`, and (4) checkout UI branching on `mode`.

**Primary recommendation:** Build **two** adapters, not three. `InterswitchAdapter` and `GtpayAdapter` share a common WebPay hash/requery core but differ enough (different endpoint hosts, different field names, different requery URL) that D-12's "one adapter, two toggles" should be implemented as **one shared internal module with two thin adapter wrappers/config objects**, not a single adapter that silently branches. `RemitaAdapter` is separate (RRR pre-step, JSONP response, naira amounts, different hash inputs). Use raw `fetch` for all three — there are no maintained Node SDKs. Reuse the existing schema (no `db:push` needed).

### Pattern 1: `initPayment` discriminated union (D-16)

**What:** Evolve the adapter return from `Record<string, unknown>` to a tagged union so `CheckoutForm` knows whether to open a popup or redirect.
**When to use:** Every adapter's `initPayment`.
**Example:**
```typescript
// src/lib/payments/gateways/types.ts (EXTEND)
export type GatewayProvider =
  | "paystack" | "flutterwave"
  | "interswitch" | "gtpay" | "remita"   // D-18

// D-16: adapters declare how the client proceeds
export type InitResult =
  | { mode: "popup"; [k: string]: unknown }        // Paystack/Flutterwave (existing data)
  | { mode: "redirect"; url: string }              // Interswitch/GTPay/Remita hosted page

// initPayment now returns Promise<InitResult>
```
Paystack/Flutterwave migration is mechanical: wrap the current return object with `{ mode: "popup", ... }`. Their panels already read the same fields; only `CheckoutForm`'s branch and the panel gain a `mode` check. This is a regression-safe refactor — keep the existing tests green.

### Pattern 2: Interswitch WebPay redirect POST + request hash

**What:** WebPay is a **form POST redirect** (not a URL GET). The adapter returns the target URL + the signed field set; the client submits an auto-POST form (or the init action returns a self-submitting form URL). Simplest: return `{ mode: "redirect", url }` where the panel renders/submits a hidden form to the POST endpoint with the computed fields.
**When to use:** Interswitch + GTPay init.
**Request hash (SHA-512, plain — NOT HMAC):**
```typescript
// Source: sandbox.interswitchng.com/docbase/docs/webpay/payment-transaction-leg/request-hash-calculation/
// Concatenation ORDER MATTERS. merchant_code is NOT in the hash.
import crypto from "crypto"
const hashInput =
  txn_ref + product_id + pay_item_id + amount + site_redirect_url + macKey  // macKey = 128-char MAC key
const hash = crypto.createHash("sha512").update(hashInput).digest("hex")
// submit as POST field "hash"; amount is in KOBO (e.g. 125000 = ₦1,250)
```
**Fields POSTed:** `merchant_code`, `pay_item_id`, `product_id`, `amount` (kobo), `currency` (566 = NGN), `site_redirect_url`, `txn_ref`, `cust_id`/`cust_email`, `hash`.
**Endpoints:** live `https://webpay.interswitchng.com/collections/w/pay`; test `https://sandbox.interswitchng.com/collections/w/pay`.

### Pattern 3: Interswitch/GTPay requery (authoritative verify)

**What:** On return, ignore the redirect params and requery the gateway server-side for the true status + amount (D-15).
**Interswitch requery:**
```typescript
// Source: docs.interswitchgroup.com/docs/web-checkout + requery-pending-transactions docbase
// GET gettransaction.json?merchantcode=&productid=&transactionreference=&amount=
// Header:  Hash: SHA-512( product_id + txn_ref + macKey )      ← requery hash order differs from request hash
const requeryHash = crypto.createHash("sha512")
  .update(product_id + txn_ref + macKey).digest("hex")
// live:  https://webpay.interswitchng.com/collections/api/v1/gettransaction.json
// test:  https://sandbox.interswitchng.com/collections/api/v1/gettransaction.json
// Response: { ResponseCode, ResponseDescription, Amount, ... }  — "00" = successful; Amount in kobo
```
**GTPay requery:** `GET https://ibank.gtbank.com/GTPayService/gettransactionstatus.json?mertid=&amount=&tranxid=&hash=` where `hash = SHA-512( mertid + tranxid + hashkey )`.
**Amount guard:** compare returned amount (kobo) `>= order.totalKobo` before confirming (Pitfall: tampering).

### Pattern 4: GTPay request (shared WebPay core, different surface — D-12)

```typescript
// Source: ibank.gtbank.com/gtpay/integrationapi/mman-tech.html
// POST https://ibank.gtbank.com/GTPay/Tranx.aspx
// Request hash (SHA-512, plain):
const gtpayHash = crypto.createHash("sha512").update(
  gtpay_mert_id + gtpay_tranx_id + gtpay_tranx_amt + gtpay_tranx_curr +
  gtpay_cust_id + gtpay_tranx_noti_url + hashkey
).digest("hex")
// Fields: gtpay_mert_id, gtpay_tranx_id (6-60 chars), gtpay_tranx_amt (KOBO),
//         gtpay_tranx_curr (566), gtpay_cust_id, gtpay_tranx_noti_url, gtpay_hash, gtpay_gway_name?
// Notification/verify response hash (server→server, gtpay_tranx_noti_url):
//   SHA-512( gtpay_tranx_id + gtpay_tranx_amt_small_denom + gtpay_tranx_status_code + gtpay_tranx_curr + hashkey )
```
**Parametrization surface (one shared core, two configs):** endpoint host, field-name map (`product_id`↔`gtpay_mert_id`-family), request-hash concat order, requery URL, requery-hash concat order. Everything else (amount unit = kobo, currency 566, redirect flow, confirmOrderPaid funnel) is identical.

### Pattern 5: Remita RRR-inside-init + redirect (D-17)

**What:** Remita requires generating an RRR (Remita Retrieval Reference) server-side first, THEN redirecting the customer to a hosted page keyed by that RRR. D-17 mandates this happens inside `initPayment`.
**Step 1 — generate RRR:**
```typescript
// Source: demo.remita.net / login.remita.net standard integration
// POST {base}/remita/exapp/api/v1/send/api/echannelsvc/merchant/api/paymentinit
//   base: demo=https://demo.remita.net  live=https://login.remita.net
// Header: Authorization: remitaConsumerKey=<merchantId>,remitaConsumerToken=<apiHash>
//         Content-Type: application/json
const apiHash = crypto.createHash("sha512")
  .update(merchantId + serviceTypeId + orderId + amount + apiKey).digest("hex")
// body: { serviceTypeId, amount, orderId, payerName, payerEmail, payerPhone, description }
// amount is NAIRA (major units) — e.g. "10000" = ₦10,000 (Pitfall 1: NOT kobo)
// Response is JSONP-wrapped: strip "jsonp (" ... ")" then JSON.parse.
//   statuscode "025" == success; RRR field carries the 12-digit reference.
```
**Step 2 — redirect URL:**
```
https://login.remita.net/remita/onepage/payment/init.reg?rrr={RRR}&channel=CARD,USSD,ENAIRA,TRANSFER
(demo host: https://demo.remita.net/...)
```
**Step 3 — verify (requery) on return:**
```typescript
// GET {base}/remita/exapp/api/v1/send/api/echannelsvc/{merchantId}/{rrr}/{statusHash}/status.reg
const statusHash = crypto.createHash("sha512")
  .update(rrr + apiKey + merchantId).digest("hex")
// Response: { status, message, amount, ... }  — "00"/"01" = successful (verify against docs at sandbox time);
// amount is NAIRA → adapter must ×100 to normalize to kobo in VerifyResult (mirror Flutterwave)
```

### Anti-Patterns to Avoid

- **Trusting redirect-return params** (`resp`, `apprAmt`, `mac` on the URL) as proof of payment. Always requery server-side (D-15). The return params are a hint that triggers the requery, nothing more.
- **A single monolithic `InterswitchAdapter` that hides `if (provider === "gtpay")`.** They diverged in surface (host, field names, requery URL). Use a shared config-driven core + two wrappers.
- **Passing kobo to Remita or naira to Interswitch/GTPay.** Interswitch/GTPay = kobo; Remita = naira. Getting this wrong is the 100× bug (Pitfall 1).
- **Redirecting the customer to `/order/[token]` before the requery returns confirmed.** Verify first, then redirect (mirror the Phase 7 `verify-before-redirect` panel pattern).
- **Exporting `runtime = "nodejs"` from the callback/webhook routes.** Node is the default; explicit export breaks `cacheComponents:true` (established Phase 4/7 constraint).

This phase should touch **zero** of the shared confirmation/idempotency/decrement/schema code — if a plan proposes changing `confirmOrderPaid` or adding order columns, that's a red flag.

## Common Pitfalls

### Pitfall 1: Amount-unit mismatch (the 100× bug) — DIFFERS per gateway
**What goes wrong:** ₦1,250 order charged as ₦125,000 (or ₦12.50), or requery amount-guard always failing.
**Why it happens:** Interswitch and GTPay expect **kobo** (like Paystack/Stripe). Remita expects **naira** (major units, like Flutterwave). The codebase stores `totalKobo`.
**How to avoid:** Interswitch/GTPay → pass `totalKobo` unchanged. Remita → pass `totalKobo / 100` on init and `× 100` when reading the verify response. Add the same `> ₦1M` sanity guard the FlutterwaveAdapter uses. Normalize `VerifyResult.amountKobo` to kobo for ALL three so the amount guard (`v.amountKobo >= order.totalKobo`) is uniform.
**Warning signs:** Requery amount guard rejecting valid payments; test amounts off by 100×.

### Pitfall 2: Hash concatenation order / whitespace
**What goes wrong:** Gateway rejects the payment with an invalid-hash error, or requery returns "invalid hash."
**Why it happens:** SHA-512 hashes are order-sensitive and the **request hash order differs from the requery hash order** (Interswitch request = `txn_ref+product_id+pay_item_id+amount+site_redirect_url+macKey`; requery = `product_id+txn_ref+macKey`). The 128-char MAC key easily picks up stray whitespace/newlines when copied into env.
**How to avoid:** Encode the exact concat order in code with a comment citing the source. Trim env values. Unit-test the hash against a known fixture. Interswitch docs explicitly warn "be wary of extra characters and spaces when working with the MAC Key."
**Warning signs:** Consistent hash-rejection in sandbox despite correct fields.

### Pitfall 3: Trusting the redirect return instead of requerying (Tampering)
**What goes wrong:** A customer edits the return URL params (`resp=00`, `apprAmt`) and gets a free order.
**Why it happens:** The gateway redirects back with status params in the URL/POST body, which are attacker-controllable.
**How to avoid:** D-15 — the callback route MUST call `verifyTransaction` (server-side requery) and check `status === confirmed && amountKobo >= order.totalKobo` before `confirmOrderPaid`. Never read the return params as authority. (Directly mirrors the Phase 7 verify-on-callback amount guard, `paystack.ts` action L170.)
**Warning signs:** Any code path that flips an order to confirmed based on redirect params.

### Pitfall 4: Idempotency-key collision between requery and webhook
**What goes wrong:** Both the verify-on-return and a later webhook confirm the same order → double email / double decrement attempt.
**Why it happens:** If the two paths use different `eventId` values, the `processed_webhook_events` ON CONFLICT guard won't collide them.
**How to avoid:** Use a **deterministic `<provider>:<ref>` key** on BOTH paths, exactly like Phase 7 (`"paystack:"+reference`, `"flutterwave:"+txRef`). Recommended: `"interswitch:"+txn_ref`, `"gtpay:"+gtpay_tranx_id`, `"remita:"+rrr` (or `"remita:"+orderId` — pick the id both the requery and the webhook reliably carry). The RRR is the stablest Remita key present in both.
**Warning signs:** Two `processed_webhook_events` rows for one payment.

### Pitfall 5: Remita JSONP response parsing
**What goes wrong:** `JSON.parse` throws because Remita's `paymentinit`/`status.reg` responses are wrapped in a JSONP callback like `jsonp(...)`.
**Why it happens:** Legacy Remita e-channel endpoints return JSONP, not clean JSON.
**How to avoid:** Strip the wrapper (`response.replace(/^\s*[A-Za-z_]+\s*\(/, "").replace(/\)\s*;?\s*$/, "")`) before `JSON.parse`. Handle both wrapped and unwrapped defensively. Verify the exact shape against the live sandbox response during D-19 sandbox testing. **[MEDIUM confidence — confirm at implementation time.]**
**Warning signs:** JSON parse errors on Remita responses only.

### Pitfall 6: Redirect leaves the site — abandoned/dropped return
**What goes wrong:** Customer closes the hosted page or the return network-drops → order stuck `pending_payment`.
**Why it happens:** Full-page redirect means the customer may never hit the callback route.
**How to avoid:** D-14/D-15 fallback — the order page (`/order/[token]`) shows the "Payment processing…" interstitial and polls `/api/order/status/[token]`; a webhook (where supported) or a manual requery resolves it. This is why verify-on-return is primary but not sole. No new cron (D-15).
**Warning signs:** Orders sitting in `pending_payment` after gateway shows success.

### Pitfall 7: Status-string normalization per gateway
**What goes wrong:** A confirmed payment mapped to `pending`/`failed`.
**Why it happens:** Each gateway uses different success markers: Interswitch `ResponseCode "00"`, GTPay `gtpay_tranx_status_code "00"`, Remita `status "00"/"01"` (confirm at sandbox). None use Paystack's `"success"` or Flutterwave's `"successful"`.
**How to avoid:** Each adapter's `verifyTransaction` maps its native code to `NormalizedStatus` ("confirmed"/"failed"/"pending"), exactly as the existing adapters do (`types.ts` NormalizedStatus). Unit-test the mapping.
**Warning signs:** Confirmed sandbox payments not flipping the order.

### Redirect callback route skeleton (verify-on-return, D-14/D-15)
```typescript
// src/app/api/payments/interswitch/callback/route.ts
// Do NOT export runtime. Toggle check FIRST. Requery, never trust return params.
import { NextRequest, NextResponse } from "next/server"
import { isPaymentMethodEnabled } from "@/lib/payments/config"
import { getOrderByGatewayReference } from "@/lib/orders/queries"
import { confirmOrderPaid } from "@/lib/payments/shared/confirm-order-paid"
import { interswitchAdapter } from "@/lib/payments/gateways/interswitch"

export async function GET(req: NextRequest): Promise<NextResponse> {
  if (!isPaymentMethodEnabled("interswitch"))
    return NextResponse.redirect(new URL("/checkout?error=disabled", req.url))

  const ref = req.nextUrl.searchParams.get("txnref") ?? ""     // hint only
  const order = await getOrderByGatewayReference(ref)
  if (!order) return NextResponse.redirect(new URL("/checkout?error=notfound", req.url))

  const v = await interswitchAdapter.verifyTransaction(ref)     // D-15 requery (authoritative)
  if (v.status !== "confirmed" || v.amountKobo < order.totalKobo)
    // inconclusive → land on order page; interstitial + polling resolves (D-14 fallback)
    return NextResponse.redirect(new URL(`/order/${order.guestToken}`, req.url))

  const result = await confirmOrderPaid(order, {
    provider: "interswitch",
    eventId: "interswitch:" + ref,        // same key a webhook would use (Pitfall 4)
  })
  if (result.outcome === "oversold")
    await interswitchAdapter.refund(ref).catch(console.error)

  return NextResponse.redirect(new URL(`/order/${order.guestToken}`, req.url))
}
```

### Known Threat Patterns for redirect-native NGN gateways

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Tampered redirect-return params (`resp=00`, `apprAmt`) | Tampering / Elevation | Ignore return params; server-side requery is sole authority (D-15). Amount guard `>= totalKobo`. |
| Forged webhook/notification to `noti_url` | Spoofing | Verify the SHA-512 notification hash (GTPay: mert-derived; Remita: rrr-derived) before `confirmOrderPaid`; toggle check first. |
| Replayed webhook / double requery | — (idempotency) | `<provider>:<ref>` key + `processed_webhook_events` ON CONFLICT DO NOTHING (existing). |
| Client price manipulation | Tampering | Total always recomputed server-side in `buildOrderContext()` (CLAUDE.md). |
| Secret leakage to client | Information Disclosure | MAC key / apiKey / hash key are server-only (`import "server-only"`); only the redirect URL reaches the client — no secret in it. |
| Oversell on last-unit race | — | Atomic `WHERE stock >= qty` in `confirmOrderPaid` + gateway `refund()` on oversold (existing D-09 path). |
