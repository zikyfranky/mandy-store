<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client UI → init action | The panel calls the server init action; the server (not the panel) enforces the toggle and recomputes the total (defense-in-depth: UI hiding is not the security boundary, UI-SPEC §5) |
| gateway return → /checkout | `?error=` query param is display-only; it drives a banner, never a payment-state decision |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-71-19 | Elevation of Privilege | RedirectLauncherPanel | mitigate | Panel is client-side convenience only; the init action re-checks isPaymentMethodEnabled first (plan 04). A disabled gateway is absent from enabledMethods AND rejected server-side (UI-SPEC §5, defense-in-depth) |
| T-71-20 | Tampering | ?error= banner | accept | Query param only selects a static banner string; carries no trust and touches no order state (UI-SPEC §4e) |
| T-71-21 | Information Disclosure | POST auto-submit fields | mitigate | The fields are the non-secret WebPay POST params (merchant code, amount, currency, redirect URL, hash) — the MAC/hash KEY is never among them (it produced the hash server-side, plan 02) |
</threat_model>
