# Phase 7.1 — UI Design Contract

> Visual and interaction contract for the three new redirect-native NGN gateways (Interswitch, GTPay, Remita) at checkout. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Guiding principle (reuse-first):** This phase adds ZERO net-new visual language. Every entry and panel MUST mirror the existing Phase 7 Paystack/Flutterwave pattern byte-for-byte in structure, spacing, token usage, icon treatment, and error markup. The ONLY genuinely new interaction wrinkle is the redirect launch (D-13) — and even that is designed to look identical to the customer: one "Place order" button, then a full-page navigation. See §4c / §4d.

## Color

60/30/10 split sourced from `src/app/globals.css` tokens (light mode / dark mode). This phase adds NO new colors.

| Role | Value (light / dark) | Usage |
|------|----------------------|-------|
| Dominant (60%) | `--background` `#f7f7fb` / `#08080c` | Page background behind the checkout card |
| Secondary (30%) | `--surface` `#ffffff` / `#131320`; `--border` `#e7e7ee` / `#26263a` | Payment section card, radio cards, panel containers, hairline dividers |
| Accent (10%) | `--brand` `#4f46e5` / `#818cf8` (+ `--brand-strong`, `--brand-soft`) | See reserved-for list |
| Destructive | `--stock-out` `#dc2626` / `#f87171` (on `red-50`/`red-500/10` banner surface) | Error banner icon + title + body; only failure states |

**Accent (`--brand`) reserved for — this phase ONLY these elements:**
1. The selected radio card border + ring + soft-wash background (`border-brand ring-2 ring-brand bg-brand-soft`) — selected-state affordance.
2. The icon chip background (`bg-brand-soft`) and the gateway icon fill (`text-brand`) inside each radio card.
3. The primary "Place order" CTA background (`bg-brand hover:bg-brand-strong`, white text) and its focus ring (`ring-brand`).
4. Focus-visible rings on interactive controls (`focus-visible:ring-brand`).

Accent is NEVER applied to body text, descriptions, dividers, or non-selected cards. There is no second brand color and no per-gateway brand coloring — Interswitch/GTPay/Remita use the SAME indigo treatment as Paystack/Flutterwave (flat peer list, D-05, no marketing hierarchy).

**Warning/neutral surfaces (inherited, reused verbatim):**
- Redirect-cancelled / abandoned notice reuses the **error banner** (red) markup — see §6.
- "No payment methods enabled" reuses the existing amber banner in `CheckoutForm` (unchanged by this phase).

| Component | Disposition | Basis | Notes |

| `CheckoutForm.tsx` | **EXTEND** | itself | Add 3 `selectedMethod === "…" ? <…Panel/>` branches in the panel chain (after the flutterwave branch, before bank_transfer). Add 3 imports. ## §4 Interaction & Visual Contracts

### §4a — New radio entries (extend `METHOD_CONFIGS`)

Each new entry MUST match the exact `MethodConfig` shape (`label`, `description`, `icon`) and render inside the identical `<label role="radio">` card the existing methods use. Do NOT add badges, "redirect" tags, or any visual marker distinguishing redirect gateways from popup gateways — the flat peer list (D-05) has no hierarchy.

- **Icon treatment:** 20px Heroicon (`w-5 h-5 text-brand`), centered in the `w-10 h-10 rounded-lg bg-brand-soft` chip — identical to Paystack's `BoltIcon` / Flutterwave's `GlobeAltIcon`.
- **Recommended Heroicons** (planner may substitute any Heroicon that reads as "payment/redirect", but MUST use the same `text-brand` 20px inline-SVG treatment):
  - Interswitch → `ArrowsRightLeftIcon` (switch/interchange metaphor)
  - GTPay → `CreditCardIcon` (bank card) — note: distinct instance is fine even though Stripe also uses a card icon; the label disambiguates.
  - Remita → `BanknotesIcon`
- **Selected state:** unchanged — `border-brand ring-2 ring-brand bg-brand-soft`; unselected `border-border bg-surface hover:border-brand/50`.
- **Accessibility:** the visually-hidden `<input type="radio" className="sr-only">` + `role="radio" aria-checked` pattern is preserved verbatim; the new methods are keyboard-reachable exactly like the existing ones.

Also update the type union in `METHOD_CONFIGS` (`Record<"stripe" | "bank_transfer" | "paystack" | "flutterwave" | "interswitch" | "gtpay" | "remita", …>`) and the `renderableMethods` filter guard so the three new methods pass through (PayPal remains filtered out, D-05a).

### §4b — Panel container (all three)

Identical to every existing panel:
```
<div className="mt-4 rounded-xl border border-border p-4 space-y-4">
  {error banner if present}
  {redirect helper <p> — §4c}
  {Place order CTA — §4d}
</div>
```
No card of its own beyond this container (the panel already sits inside the §4 Payment `<section>` card).

### §4c — Redirect launcher pre-redirect state (the one new element)

Above the CTA, render a single muted helper line (this is the ONLY net-new visual element in the whole phase):
```
<p className="text-sm text-muted">
  You'll be securely redirected to {Gateway} to complete your payment, then brought back here.
</p>
```
- `text-sm text-muted` = 14px, `--muted` color — matches the existing "Card fields will appear after clicking Place order" helper in the Stripe panel.
- No gateway logo, no iframe, no inline card fields (these gateways have no clean inline popup — D-13). The helper line sets the expectation that a redirect is coming, so the full-page navigation is not jarring.

### §4d — CTA + redirect launch (POST vs GET, identical to the user)

The CTA is the EXACT existing button (verbatim classes):
```
w-full rounded-xl bg-brand hover:bg-brand-strong text-white px-6 py-4 text-base font-semibold
transition-colors focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-brand
focus-visible:ring-offset-2 disabled:opacity-50 disabled:cursor-not-allowed
flex items-center justify-center gap-2
```
- Default label: `LockIcon` + **"Place order"**.
- Submitting label: `SpinnerIcon animate-spin` + **"Processing…"**.
- `disabled={isSubmitting || hasOOS}` + `aria-disabled` + the same `hasOOS` aria-label — verbatim from existing panels.

**Launch behavior on the returned D-16 union (must look identical to the customer — a single tap → the button enters "Processing…" → full-page navigation):**

| Gateway | Redirect kind | Client action |
|---------|---------------|---------------|
| Remita | GET (`{mode:"redirect", url}`) | `window.location.assign(url)`. Button stays in "Processing…" during navigation (never re-enable on the success path — mirror Stripe redirect). |
| Interswitch | POST auto-submit | The init action returns the POST target + signed fields (shape is planner's call — e.g. `{mode:"redirect", url, method:"POST", fields}`). The panel builds a hidden `<form method="POST" action={url}>` with `<input type="hidden">` per field, appends to `document.body`, and calls `form.submit()` immediately. To the customer this is indistinguishable from the GET case — the button shows "Processing…" then the page navigates. |
| GTPay | POST auto-submit | Same hidden-auto-submit-form mechanism as Interswitch. |

The hidden POST form is **never visible** (no rendered fields, submitted in the same tick the response arrives). There is no intermediate "confirm redirect" screen. This keeps all three gateways visually identical to each other and as close as possible to the Stripe/Paystack "one button" feel (CONTEXT specifics).

**Validation-before-launch:** call `await trigger()` first (address/email validation) exactly like the existing panels; only launch the redirect if valid. Init errors surface in the error banner and re-enable the button (§6).

### §4e — Redirect-return UX (D-14)

The customer returns to the server callback route (`/api/payments/<gw>/callback`), which verifies then `NextResponse.redirect`s. There are three terminal UI destinations, all EXISTING surfaces — no new page:

1. **Verified (happy path):** callback redirects to `/order/[guestToken]`. The order is `payment_confirmed` → `OrderConfirmedView` renders instantly (same end-state as Stripe/Paystack success). **Transitional state:** while the server callback runs its requery and the order page streams, the browser shows the existing `OrderPageSkeleton` (Suspense fallback) — a pulse-skeleton card. No spinner page of our own; the redirect chain is fast and the skeleton covers the gap.
2. **Verify inconclusive at return (abandoned mid-verify / gateway slow):** callback still redirects to `/order/[guestToken]`, but order is `pending_payment` → the EXISTING `PaymentProcessingView` shows the "Payment processing…" interstitial and polls `/api/order/status/[token]` (D-14/D-15 backstop). A later webhook or poll flips it to confirmed and the view swaps to `OrderConfirmedView` (existing prop-swap behavior). No new component.
3. **Cancelled / gateway error / disabled / not-found return:** callback redirects back to **`/checkout?error=cancelled`** (or `=disabled` / `=notfound`). `CheckoutForm` reads the query param on mount and shows the reused red error banner with the matching copy (§6). The customer can immediately retry — the form state is fresh. This mirrors the Paystack/Flutterwave `onCancel`/`onClose` "stay and retry" behavior, adapted to the redirect model (there's no client callback, so the signal comes via the query param the callback route sets).

## §5 Disabled / Gated States

- **Gateway toggled OFF server-side:** the method is absent from `enabledMethods` (computed by `enabledPaymentMethods()` server-side, D-18/D-06), so its radio entry is **never rendered** and no panel exists. There is NO greyed-out or "coming soon" entry — absence is the disabled UI (matches existing Stripe/Paystack behavior). No client-side toggle logic.
- **All methods off:** existing amber "Payment unavailable" banner in `CheckoutForm` (unchanged).
- **Out-of-stock item in cart (`hasOOS`):** the CTA is disabled with the existing aria-label "Remove out-of-stock items from your cart before placing an order" — reused verbatim, no new copy.
- **Server-side rejection is authoritative:** even if a disabled gateway's panel were somehow rendered, the init action rejects with `{ error: "…" }` (first-statement toggle check, D-18) → surfaced in the error banner. UI hiding is defense-in-depth, not the security boundary.

## §6 Error States (all reuse the existing red banner)

Every error uses the identical banner markup (`role="alert" aria-live="assertive"`, `rounded-xl bg-red-50 dark:bg-red-500/10 border border-red-200 dark:border-red-500/30 p-4 flex gap-3 items-start`, ExclamationIcon `text-stock-out`, semibold title + `text-red-700 dark:text-red-300` body). No new error UI is designed.

| Scenario | Where shown | Title | Body |
|----------|-------------|-------|------|
| Init / redirect-launch failure (network, action `{error}`) | Panel error banner (`/checkout`) | Order could not be started | Something went wrong starting your payment. Please check your connection and try again. |
| Init rejected — gateway disabled server-side | Panel error banner | Order could not be started | (the action's `{error}` string, e.g. "Interswitch is not available") |
| Cancelled / abandoned return (`?error=cancelled`) | CheckoutForm banner on mount | Payment cancelled | Payment cancelled — you can try again. |
| Verify inconclusive | none on checkout | — | Lands on `/order/[token]` → existing "Payment processing…" interstitial + polling |
| Payment ultimately failed | existing `/order/[token]` failed-state card | Payment could not be processed | (existing copy + "Return to checkout" CTA — unchanged) |

Button re-enable rule (verbatim from existing panels): on ANY error path that does NOT navigate away, set `isSubmitting = false` so the button returns to "Place order". On the success redirect path, leave it disabled (the page is navigating).

## §7 Things That CANNOT Reuse an Existing Component (flagged)

Per the focus directive, explicitly flagging every net-new surface. The list is deliberately tiny:

1. **The redirect helper `<p>` line (§4c)** — new *copy*, but reuses the existing `text-sm text-muted` treatment (same style as the Stripe panel's helper text). Not a new component, just new text in an existing style.
2. **The hidden POST auto-submit `<form>` (§4d, Interswitch/GTPay)** — genuinely new markup with no visual footprint (never rendered visibly, submitted in the same tick). This is the only truly novel DOM this phase introduces, and by design it is invisible. It exists solely to express "redirect via POST" through the D-16 union (RESEARCH open question 3). Remita needs none of this (plain GET).
3. **The `?error=cancelled` query-param → banner read on mount in `CheckoutForm` (§4e)** — new *wiring* (a `useEffect`/searchParams read), but it drives the EXISTING error banner. No new visual component.

Everything else — radio card, panel container, CTA button, error banner, spinner/lock icons, order confirmation page, processing interstitial, skeleton — is a verbatim reuse or a structural mirror. **No new confirmation page, no new modal, no new spinner screen, no per-gateway branding.**
