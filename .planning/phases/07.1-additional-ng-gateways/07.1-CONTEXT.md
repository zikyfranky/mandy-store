# Phase 7.1: Additional NG Gateways (fast-follow) - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Add the **direct-integration** NGN gateways as **new adapters against the Phase 7
`GatewayAdapter` interface** (D-02), each independently server-toggleable and reusing the
Phase 7 shared idempotent `confirmOrderPaid()` confirmation path. This is a fast-follow on
Phase 7 (Paystack + Flutterwave aggregators) — no net-new payment plumbing, just new adapters
+ toggle cases + checkout entries.

**Requirements addressed:** PAY-07 (Opay), PAY-08 (Palmpay), PAY-09 (Interswitch),
PAY-10 (GTPay), PAY-11 (Remita).

**Scope after re-evaluation (D-11):** The roadmap and Phase 7 CONTEXT both flagged that
Opay/Palmpay already ride the Paystack/Flutterwave popups *as channels* (~90% NGN coverage
shipped in Phase 7). This phase therefore builds **only the genuinely-additive direct gateways
— Interswitch, GTPay, Remita** — as standalone adapters/buttons. **Opay (PAY-07) and Palmpay
(PAY-08) are marked satisfied-via-channel** (reachable through the existing aggregator popups),
not built as redundant standalone buttons.

**Out of scope (other phases / deferred):**
- Standalone Opay/Palmpay direct-API buttons — deemed redundant (satisfied-via-channel). Revisit
  only if a concrete need for a top-level Opay/Palmpay button emerges.
- Scheduled/cron reconciliation infrastructure for flaky webhooks → its own phase if ever needed
  (D-15 chose the no-new-infra polling backstop instead).
- Admin manual confirmation / fulfillment → Phase 5.
- Passing gateway transaction fees to the customer → deferred (v2 pricing capability).
- PayPal → remains deferred (no NGN).

</domain>

<decisions>
## Implementation Decisions

### Gateway scope (which to build)
- **D-11:** **Build Interswitch, GTPay, Remita only** as standalone direct-integration adapters.
  **Opay (PAY-07) + Palmpay (PAY-08) are satisfied-via-channel** through the Phase 7
  Paystack/Flutterwave inline popups — do NOT build standalone Opay/Palmpay buttons/adapters.
  Rationale: the roadmap's own re-evaluation note — aggregators already reach Opay/Palmpay as
  channels, so standalone buttons duplicate UX for near-zero marginal reach.
- **D-12:** **GTPay is a config variant of a single shared `InterswitchAdapter`, not a separate
  code path.** GTPay is GTBank's gateway running on Interswitch WebPay/QuickTeller infrastructure
  (same hash scheme, same redirect/verify flow) — parametrize one adapter by merchant config and
  expose GTPay as a second toggle/case. PAY-09 + PAY-10 satisfied by one adapter, two toggles.
  (Research should confirm the WebPay integration is still shared in 2026 before finalizing, but
  the decision is: shared unless research proves they diverged.)

### Flow model (holds/relaxes Phase 7 D-03/D-05 "never leaves the site")
- **D-13:** **Relax "never leaves the site" for redirect-native gateways.** Interswitch WebPay
  and Remita use a full-page redirect to the gateway's hosted checkout, then return to our
  callback URL — they do not offer the clean inline popup Paystack/Flutterwave do. Flow:
  `initPayment` (server-side, order already created via `buildOrderContext`) → redirect to hosted
  page → gateway → return to our callback route. Inline stays the pattern for any gateway that
  supports it; redirect is used only where the gateway requires it.
- **D-14:** **Redirect-return UX = verify then confirmation page.** The callback route runs
  server-side `verifyTransaction` → shared `confirmOrderPaid()` → redirects straight to the order
  confirmation page (same instant end-state as Stripe/Paystack success). The existing "Payment
  processing…" interstitial + `/api/order/status/[token]` polling (Phase 4 D-07) is the fallback
  only when verify is inconclusive at return.

### Confirmation authority for redirect gateways (nuances Phase 7 D-04/D-06)
- **D-15:** **Verify-on-return is the PRIMARY authority for redirect gateways** (server-side
  re-fetch from the gateway — never trust client-supplied amount/status), because
  Interswitch/Remita webhook/notification support is weaker/less consistent than the aggregators.
  Consume each gateway's webhook/notification **when it exists** (signature/hash-verified, funneled
  through the *same* idempotent `confirmOrderPaid()` path). If neither confirms, the "Payment
  processing…" interstitial + status polling re-queries `verifyTransaction` as the backstop.
  **No new cron/queue infrastructure.** This is a deliberate per-gateway shift from Phase 7's
  webhook-is-ultimate-authority model, justified by these gateways' webhook reliability — the
  idempotency guard still makes whichever signal arrives first win, the rest no-ops.

### Adapter contract shape (extends Phase 7 D-02)
- **D-16:** **`initPayment` returns a typed discriminated union** instead of the current loose
  `Record<string, unknown>`: conceptually `{ mode: "popup", ...popupData } | { mode: "redirect",
  url }`. Adapters declare how the client proceeds; `CheckoutForm` branches on `mode`. Existing
  Paystack/Flutterwave adapters migrate to `{ mode: "popup", ... }` (regression-safe refactor).
- **D-17:** **Remita's RRR (Remita Retrieval Reference) generation happens INSIDE
  `initPayment`** before returning the redirect URL — hidden from callers, keeps the adapter the
  sole authority over provider-specific pre-steps. Callers never see gateway-specific mechanics.
- **D-18:** Extend `GatewayProvider` union + `isPaymentMethodEnabled` switch + `enabledPaymentMethods`
  list + `PaymentMethodSelector`/`CheckoutForm` branching with the new gateways (mechanical,
  mirrors the Phase 7 Paystack/Flutterwave extension). Each new gateway follows D-06: enabled ⇔
  `ENABLE_<GATEWAY>=true` AND required secret(s) present; server-side rejection is the first
  statement in every new action/route.

### Definition of done / go-live bar
- **D-19:** **"Done" = adapter implemented + passing against each gateway's sandbox/test env,
  with the toggle OFF by default** (enabled per D-06 only when live `ENABLE_<GATEWAY>=true` +
  secrets present). Mirrors Phase 7's "code complete, live-verify pending" — does not block on
  external enterprise merchant onboarding timelines. PAY-09/PAY-10/PAY-11 are marked complete at
  the sandbox bar; live-verification is a go-live checklist item. PAY-07/PAY-08 marked
  satisfied-via-channel (D-11).

### Claude's Discretion
- Exact TypeScript shape of the `initPayment` discriminated union (D-16) — intent locked, shape
  is planner's call.
- Whether the redirect callback is one dispatched route or per-gateway routes; file layout under
  `src/lib/payments/gateways/*`.
- Interswitch/GTPay hash algorithm specifics, Remita RRR API details, per-gateway idempotency
  event-id sourcing — research/planner territory (see research flags).
- How much of the Interswitch WebPay logic GTPay shares vs. overrides within the shared adapter
  (D-12) — planner decides the parametrization boundary.

</decisions>

<specifics>
## Specific Ideas

- Keep redirect gateways feeling as close to the Stripe/aggregator experience as possible: the
  customer should return from the hosted page straight into the normal order-confirmation page,
  not a dead-end or a manual "check status" screen.
- Interswitch and GTPay should not feel like two separate integrations to maintain — they're one
  gateway with two merchant configs (D-12).
- Redirect gateways should degrade gracefully: if the customer abandons the hosted page or the
  return is dropped, the existing "Payment processing…" interstitial + polling must still resolve
  the order (D-14/D-15).

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`GatewayAdapter` interface + `VerifyResult`** (`gateways/types.ts`) — the D-02 extension seam;
  new gateways implement it. `initPayment` return evolves to the D-16 discriminated union.
- **`confirmOrderPaid()`** (`shared/confirm-order-paid.ts`) — the idempotent confirmation core
  (idempotency insert + atomic order-flip/stock-decrement + oversold refund + email); every new
  gateway's verify-on-return + webhook path funnels through it unchanged.
- **`buildOrderContext()`** (`checkout.ts`) — server-side total recompute + order/items insert;
  reuse verbatim for new gateway init actions.
- **Toggle system** (`isPaymentMethodEnabled` / `enabledPaymentMethods`, `config.ts`) — the exact
  D-18/D-06 extension point.
- **`PaymentMethodSelector` radio + `Stripe/Paystack/FlutterwavePaymentPanel`** — pattern to
  mirror for the new gateway entries; CheckoutForm branches on the D-16 `mode`.
- **Order status machine + `processed_webhook_events` + guest token page + status-polling
  endpoint** — reused for the D-14/D-15 fallback path.

### Established Patterns
- Next.js 16 App Router; `proxy.ts` (not middleware); re-verify server-side in every action/route.
  Server-only env flags, no `NEXT_PUBLIC_` on secrets.
- Webhook/callback routes: raw `req.text()` first for signature/hash verify; idempotency-first;
  neon-http has **no `db.transaction()`** — use `db.batch` (documented atomic).
- Build: `npx next build --webpack`; Node 20+ (`.nvmrc` = 22). `next/cache` mocked in Server
  Action integration tests; vitest `fileParallelism=false`; integration tests gated on
  `TEST_DATABASE_URL`.

### Integration Points
- New gateway init Server Actions (mirror `createStripePaymentIntent`) return the D-16 union —
  `{mode:"redirect", url}` for Interswitch/GTPay/Remita.
- New redirect **callback/return route(s)** per gateway (or one dispatched route) run
  `verifyTransaction` → `confirmOrderPaid` → redirect to confirmation page (D-14). Optional webhook
  routes where the gateway supports them, funneling into the same path (D-15).
- `PaymentMethod` union + `isPaymentMethodEnabled` switch + selector/CheckoutForm branching
  extended for Interswitch/GTPay/Remita (D-18).
- Confirm whether Remita RRR reuses `gatewayReference` or needs a schema tweak (likely reuse;
  planner decides — a `db:push` may not be needed if the Phase 7 columns suffice).
