<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client checkout form → server actions | All payment/order creation is server-validated; UI only collects |
| browser → Stripe iframe | Card data is tokenized in Stripe's cross-origin iframe (SAQ-A) |
| server config → rendered methods | UI reflects enabled methods; it is not the enforcement point |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-23 | Information Disclosure | card data handling | mitigate | Stripe Payment Element renders in Stripe's iframe; card data never touches app DOM (D-05, SAQ-A); only browser-safe clientSecret + publishable key used |
| T-04-24 | Elevation of Privilege | disabled-method UI | mitigate | UI hides disabled methods AND server actions re-check isPaymentMethodEnabled (Plan 03) — UI is not the control; PayPal never rendered (D-05a/D-13) |
| T-04-25 | Information Disclosure | bank details in client | mitigate | BankTransferPanel shows no account numbers (D-10); details only appear on the server-rendered confirmation page + email (Plan 06) |
| T-04-26 | DoS / Duplicate charge | double-submit | mitigate | Place order button disabled on first click; re-enabled only on error (Pitfall 7) |
| T-04-27 | Spoofing | trusting client "paid" | mitigate | UI never marks an order paid; it redirects to /order/:token which reflects the webhook-written status (D-06) |
</threat_model>
