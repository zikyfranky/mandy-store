<objective>
Implement the two checkout Server Actions that create orders: `createBankTransferOrder` (PAY-03 — order = awaiting_bank_transfer, sends instructions email, no stock hold) and `createStripePaymentIntent` (PAY-01 — pending_payment order + Stripe PaymentIntent, returns clientSecret). Both recompute the total server-side from getCart() + flat shipping (CHKT-03/04), validate the NG address (CHKT-02), allow guest checkout (CHKT-01), and enforce payment-method toggles server-side (PAY-04).

Purpose: This is the write path that turns a cart into an order. It is the security-critical core — price tampering, disabled-method bypass, and IDOR are all designed out here. Stock is NOT decremented in either action (D-09: decrement happens only on confirmed payment in the webhook).
Output: `src/lib/actions/checkout.ts` with both actions; integration tests covering guest order creation, server total recompute, awaiting_bank_transfer status, and toggle rejection.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client form → checkout action | Untrusted email/address/payment-method-choice crosses into order creation |
| client cart → PaymentIntent amount | Amount must derive only from server-recomputed cart total |
| client method choice → enabled methods | A disabled method must be rejected server-side, not just hidden |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-10 | Tampering | PaymentIntent amount | mitigate | amount = computeOrderTotal(getCart().subtotalKobo).totalKobo; the action never reads a client-supplied amount (CLAUDE.md) |
| T-04-11 | Elevation of Privilege | disabled method bypass | mitigate | each action's FIRST statement is isPaymentMethodEnabled(...) → return {error} (PAY-04/D-13); UI hiding is not the control |
| T-04-12 | Spoofing/IDOR | order ownership | mitigate | userId comes only from auth() session, never from form; guests get userId null (CHKT-01); no client-supplied user id accepted |
| T-04-13 | Information Disclosure | bank not marked paid | mitigate | bank order hardcodes status "awaiting_bank_transfer" (Pitfall 8); stock not decremented (D-09) so no inventory leaked to unpaid orders |
| T-04-14 | Input Validation | address/email injection | mitigate | CheckoutSchema (Zod) validates email + NG state enum + required fields before any DB write |
| T-04-15 | Tampering | double-submit duplicate order | accept | UI disables submit on first click (Plan 05, Pitfall 7); a stricter server idempotency check on email+cart is deferred — low impact, customer-visible duplicate is rare |
</threat_model>
