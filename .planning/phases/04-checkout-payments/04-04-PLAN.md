1. Create `src/app/api/webhooks/stripe/route.ts`. First non-import line: `export const runtime = "nodejs"` (never edge — needs Node crypto; Pitfall 1). Imports: NextRequest/NextResponse, Stripe (type), stripe singleton, db, { processedWebhookEvents, orders, orderItems, variants } from schema, { eq, sql } from drizzle-orm, getOrderByStripePaymentIntentId, sendOrderConfirmationEmail.

`export async function POST(req: NextRequest): Promise<NextResponse>`:
- `const body = await req.text()` as the FIRST statement (raw body required; Pitfall 1 — never req.json()).
- `const sig = req.headers.get("stripe-signature") ?? ""`.
- `try { event = stripe.webhooks.constructEvent(body, sig, process.env.STRIPE_WEBHOOK_SECRET!) } catch { return NextResponse.json({ error: "Signature verification failed" }, { status: 400 }) }`.
- If `event.type !== "payment_intent.succeeded"` → `return NextResponse.json({ received: true })` (always 200 for unhandled types; Pitfall 6 note — only return clientSecret-safe data, never secrets).
- Extract `const pi = event.data.object as Stripe.PaymentIntent`.
- Idempotency-first (Pitfall 2): `const [idem] = await db.batch([ db.insert(processedWebhookEvents).values({ id: event.id, provider: "stripe" }).onConflictDoNothing() ])`. If `idem.rowCount === 0` → already processed → `return NextResponse.json({ received: true })`.
- Look up the order by PaymentIntent id: `const order = await getOrderByStripePaymentIntentId(pi.id)`. If `!order` → return 400 `{ error: "Order not found" }` (Stripe will retry; acceptable — the PI metadata.orderId is also available as a fallback: if lookup by PI id fails, try `metadata.orderId`).
- If `order.status === "payment_confirmed"` already → `return NextResponse.json({ received: true })` (defensive).
- Flip the order + decrement stock atomically. Build per-item conditional decrements using raw SQL so the WHERE stock >= qty guard is enforced (no oversell, SC5). Because neon-http db.execute returns affected-row info, run the order update + decrements in a single `db.batch([...])`:
```typescript
const decrements = order.items.map((item) =>
  db.execute(sql`UPDATE "variant" SET stock = stock - ${item.quantity} WHERE id = ${item.variantId} AND stock >= ${item.quantity}`)
)
const results = await db.batch([
  db.update(orders).set({ status: "payment_confirmed", paidAt: new Date() }).where(eq(orders.id, order.id)),
  ...decrements,
])
```
- Last-unit-race detection (D-09 / Pitfall 3): inspect each decrement result's affected row count (`results[i].rowCount` for i ≥ 1). If ANY decrement affected 0 rows, the item was oversold:
  1. `await stripe.refunds.create({ payment_intent: pi.id })`
  2. `await db.update(orders).set({ status: "payment_failed", refundReason: "oversold" }).where(eq(orders.id, order.id))`
  3. `await sendOrderConfirmationEmail(...)` is NOT sent; instead send an oversell-notification (reuse sendOrderConfirmationEmail with a different subject is acceptable for v1 OR add a brief inline note — at minimum log + attempt customer email). Do NOT throw; return 200 so Stripe does not retry the already-refunded charge.
  Document this branch with a comment citing D-09.
- On the happy path (all decrements affected 1 row): `sendOrderConfirmationEmail({ customerEmail: order.customerEmail, reference: order.reference, guestToken: order.guestToken, items: order.items.map(...), subtotalKobo: order.subtotalKobo, shippingKobo: order.shippingKobo, totalKobo: order.totalKobo }).catch(console.error)` (non-blocking; never fail the webhook on email error).
- `return NextResponse.json({ received: true })`.

NOTE on rowCount: neon-http `db.execute` returns a result with a row count field; if the exact property differs, use `RETURNING id` on the UPDATE and check the returned rows length instead (`UPDATE ... AND stock >= ${qty} RETURNING id`). Choose whichever the driver exposes reliably and assert it in the test. Document the choice in a comment.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stripe → webhook endpoint | Inbound POST is untrusted until the signature is verified against the raw body |
| webhook → DB writes | Order confirmation + stock decrement must be atomic and idempotent |
| public token → order status | Status endpoint exposes only status, keyed by the unguessable token |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-16 | Spoofing | forged webhook | mitigate | stripe.webhooks.constructEvent(rawBody, sig, STRIPE_WEBHOOK_SECRET) verifies HMAC timing-safe; req.text() read before any parse (Pitfall 1); nodejs runtime |
| T-04-17 | DoS/Tampering | webhook replay / duplicate | mitigate | insert into processed_webhook_events onConflictDoNothing FIRST; rowCount===0 short-circuits to 200; unique constraint is the true guard (Pitfall 2) |
| T-04-18 | Tampering | overselling race | mitigate | atomic conditional decrement `UPDATE variant SET stock = stock - qty WHERE id=? AND stock >= qty` inside db.batch; never read-then-write (SC5, CLAUDE.md) |
| T-04-19 | Integrity | last-unit oversell on paid order | mitigate | decrement rowCount===0 → stripe.refunds.create + status payment_failed + refundReason + customer notify; return 200 (D-09, Pitfall 3) |
| T-04-20 | Information Disclosure | status endpoint enumeration | mitigate | keyed by 64-char guestToken only; returns just { status }; unknown token → 404; no order ids exposed |
| T-04-21 | Information Disclosure | secret leakage in response | mitigate | handler returns only { received } / { status }; never STRIPE_SECRET_KEY or webhook secret (Pitfall 6) |
| T-04-22 | Repudiation | client claims paid without webhook | mitigate | webhook is the SOLE writer of payment_confirmed (D-06); client return_url never marks paid |
</threat_model>
