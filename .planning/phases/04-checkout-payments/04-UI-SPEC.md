# Phase 4 — UI Design Contract: Checkout & Payments

> Visual and interaction contract for Phase 4 frontend surfaces. Generated by gsd-ui-researcher.
> This phase EXTENDS the Phase 2/3 design system — all tokens, typography, and color are inherited.
> No new design system is introduced.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Tailwind v4 only — matches Phase 2/3; no shadcn) |
| Preset | not applicable |
| Component library | none — custom-styled primitives with Tailwind v4 utility classes |
| Icon library | Heroicons v2 (SVG, inline — same as Phases 2/3) |
| Font | Geist Sans (`var(--font-geist-sans)` — already loaded in `src/app/layout.tsx`) |
| New dependencies | `react-hook-form@7.80.0`, `@hookform/resolvers@5.4.0` (form state); `stripe@22.3.0`, `@stripe/stripe-js@9.8.0`, `@stripe/react-stripe-js@6.6.0` (Stripe Payment Element) |

**Rationale:** Phase 2 established the Tailwind v4 design system. Phase 3 inherited it verbatim. Phase 4 inherits every token verbatim again. New dependencies are behavior/payment libraries, not UI component libraries. `react-hook-form` manages the checkout address form with per-field validation; Stripe React libraries render the embedded Payment Element.

**Source:** `src/app/globals.css` (all tokens), `03-UI-SPEC.md` (spacing, typography, color, component patterns).

## Spacing Scale

Declared values — INHERITED from Phase 2/3, multiples of 4 only:

| Token | Value | Checkout Usage |
|-------|-------|---------------|
| xs | 4px | Icon gaps, inline badge padding, field hint spacing |
| sm | 8px | Field label-to-input gap, method selector option gap, order summary row gap |
| md | 16px | Form section padding, payment panel padding, method selector padding |
| lg | 24px | Form section separators, order summary card internal spacing, section headings margin |
| xl | 32px | Desktop column gap between form and order summary, page section vertical gaps |
| 2xl | 48px | Page top/bottom padding on desktop |
| 3xl | 64px | Not used in Phase 4 |

Exceptions:
- Stripe Payment Element iframe container: no explicit height — it auto-sizes; set minimum height of 48px as a loading skeleton placeholder
- Payment method selector radio cards: minimum 48px height per option (touch-safe, larger than standard field row)
- Order summary panel: `sticky top-24` (24 = 96px — clears the 64px sticky header + 32px breathing room)
- Order reference chip on confirmation page: `px-4 py-2` (16px / 8px) with `rounded-full` — pill format, not a standard form field
- "Payment processing…" spinner container: 64px height to give the pulsing animation visual room

## Typography

INHERITED from Phase 2/3 — 4-size scale, 2 weights, no additions:

| Role | Size | Weight | Line Height | Tailwind Class | Phase 4 Usage |
|------|------|--------|-------------|----------------|--------------|
| Body | 16px | 400 (regular) | 1.5 | `text-base font-normal leading-relaxed` | Field hint/helper text, payment method description, confirmation body paragraphs, bank account details prose |
| Label | 14px | 600 (semibold) | 1.4 | `text-sm font-semibold leading-snug` | Form field labels, order summary line-item names, method selector option labels, order reference chip text, status badge text |
| Heading | 24px | 600 (semibold) | 1.3 | `text-2xl font-semibold leading-tight` | Page heading "Checkout", section headings "Shipping address" / "Payment" / "Order summary", confirmation page headings |
| Display | 28px | 600 (semibold) | 1.2 | `text-3xl font-semibold leading-tight` | Confirmation success "Order confirmed!" headline only |

**Weights in use: exactly 2 — 400 (regular) and 600 (semibold). No font-medium (500) or font-bold (700).**

Special cases within the 4-step scale:
- Order total on the summary panel: `text-2xl font-semibold` (24px, 600) — same as Phase 3 subtotal treatment; key financial number reads prominently
- `text-[10px] font-semibold` exception from Phase 3 (badge bubble) is not used in Phase 4

### 6. Inline Payment Error / Retry State (D-08)

When a Stripe payment fails (card declined, insufficient funds, etc.), the customer stays on `/checkout`. The error is shown inline, and address + form state are preserved.

```
[error banner: mt-4 rounded-xl bg-red-50 dark:bg-red-500/10
               border border-red-200 dark:border-red-500/30 p-4
               flex gap-3 items-start]

  [icon: Heroicons ExclamationCircleIcon 20px text-stock-out shrink-0]

  [text group]
    [heading: text-sm font-semibold text-stock-out]
      "{Stripe error title}" — e.g. "Your card was declined"
    [body: text-sm text-red-700 dark:text-red-300 mt-1]
      "{Stripe error message + call to action}" — e.g. "Please try a different card or payment method."
```

The banner appears between the payment section card and the "Place order" button. It uses `role="alert"` `aria-live="assertive"` so screen readers announce immediately. The "Place order" button re-enables after error so the customer can retry.

Stripe-specific error mapping for common decline codes:

| Stripe decline code | Displayed message |
|---------------------|------------------|
| `card_declined` | "Your card was declined. Please try a different card or payment method." |
| `insufficient_funds` | "Insufficient funds. Please check your balance or try a different card." |
| `incorrect_cvc` | "Incorrect security code (CVC). Please check and try again." |
| `expired_card` | "Your card has expired. Please use a different card." |
| `generic_decline` | "Payment could not be processed. Please try again or use a different payment method." |
| (fallback) | "{Stripe error.message}" — pass through Stripe's message |

## Interaction Contracts

### Checkout Form Submission — Stripe Card Path

1. Customer fills email, address, selects "Debit / Credit card"
2. Stripe Payment Element mounts and shows card fields
3. Customer fills card details within Stripe element
4. Customer clicks "Place order"
5. Button enters submitting state: "Processing…" + spinner; button disabled immediately (prevent double-submit)
6. `createStripePaymentIntent(formData)` Server Action fires:
   - Validates server-side (payment method enabled, cart not empty, cart not OOS)
   - Recomputes total from `getCart()` (never trusts client)
   - Creates order row (`pending_payment`) + PaymentIntent
   - Returns `{ clientSecret, guestToken }` to client
7. Client calls `stripe.confirmPayment({ clientSecret, confirmParams: { return_url: /order/{guestToken} } })`
8. Stripe handles 3DS if needed; redirect fires to `/order/{guestToken}` on success
9. Customer lands on `/order/[token]` — either success (7a) or processing interstitial (7c)
10. On Stripe error: button re-enables; error banner (§6) appears; address + form preserved

### Checkout Form Submission — Bank Transfer Path

1. Customer fills email, address, selects "Bank transfer (NGN)"
2. The info panel (§4c) explains the process
3. Customer clicks "Place order"
4. Button enters submitting state: "Processing…" + spinner; button disabled
5. `createBankTransferOrder(formData)` Server Action fires:
   - Validates (payment method enabled, cart not empty, no OOS)
   - Recomputes total from `getCart()`
   - Creates order row (`awaiting_bank_transfer`)
   - Generates `MS-XXXXXX` reference and 64-char guest token
   - Sends bank transfer instructions email (Resend)
6. Server Action redirects to `/order/{guestToken}`
7. Customer lands on confirmation page — bank transfer awaiting state (7b) with account details

### Order Status Polling (/order/[token] processing state)

1. Server Component loads: order status is `pending_payment`
2. Processing interstitial (7c) renders — includes a client island
3. Client island starts polling `GET /api/order/status/{token}` every 2000ms
4. Poll response shape: `{ status: "pending_payment" | "payment_confirmed" | "payment_failed" }`
5. On `payment_confirmed`: client island transitions card content to success state (7a); polling stops
6. On `payment_failed`: client island renders an error state with "Your payment could not be confirmed. Please return to checkout and try again." + link back to `/checkout`
7. On 30s timeout without resolution: show fallback copy (§7c); polling continues in background but user is unblocked

### Copy Reference Button (bank transfer confirmation)

1. Customer clicks "Copy reference"
2. `navigator.clipboard.writeText("MS-7F3K2A")`
3. Button label changes to "Copied!" for 2 seconds (managed by `useState + setTimeout`)
4. Returns to "Copy reference" after 2s
5. Accessible: `aria-label` changes from "Copy order reference" to "Order reference copied" during the 2s window

## Accessibility Contracts

- /checkout page: `<main>` wrapper; page `<h1>` is "Checkout"; section headings are `<h2>` ("Contact", "Shipping address", "Payment"); order summary heading is `<h2>` "Order summary"
- /order/[token] page: `<main>` wrapper; primary heading is `<h1>` ("Order confirmed!" / "Complete your transfer" / "Payment processing…")
- Payment method selector: `role="radiogroup"` `aria-label="Payment method"` on the container; each card label has `role="radio"` `aria-checked={isSelected}`; radio `<input>` is `.sr-only` (visually hidden but in DOM for screen reader semantics)
- All form inputs: `<label>` elements with explicit `htmlFor`; no `aria-label` substituting for a visible label
- Field validation errors: `aria-invalid="true"` on the input when invalid; error message is linked via `aria-describedby` pointing to the error element's ID; `role="alert"` on the error paragraph so it announces on injection
- Payment decline error banner: `role="alert"` `aria-live="assertive"` — announces immediately when injected
- OOS warning banner: `role="status"` `aria-live="polite"` — less urgent; same amber treatment as Phase 3 clamp notice
- Processing interstitial client island: `aria-live="polite"` container so state transitions ("Order confirmed!") are announced without a page reload
- Copy reference button: `aria-label="Copy order reference"` at idle; changes to `aria-label="Order reference copied"` for 2s after click
- "Place order" button while submitting: `aria-disabled="true"` + `disabled`; screen reader hears "Processing…, button, dimmed"
- Account offer CTA: full focus ring `focus-visible:ring-2 focus-visible:ring-brand focus-visible:ring-offset-2`
- All interactive elements: minimum 44px touch target (`min-h-11 min-w-11`) — except embedded Stripe Payment Element (Stripe-owned, not adjustable)
- All focusable elements: `focus-visible:ring-2 focus-visible:ring-brand focus-visible:ring-offset-2 focus:outline-none`
- Stripe Payment Element accessibility: delegated to Stripe's embedded iframe; it meets WCAG 2.1 AA natively
- Skeleton loaders: `aria-hidden="true"` so screen readers skip them; use `aria-busy="true"` on the containing region instead

| Decision | Rationale | Source |
|----------|-----------|--------|
| Single-page /checkout with 3/5 + 2/5 column split | D-01 locked; 3/5 gives the form more width than a strict 50/50 split; accommodates address form fields without cramping | 04-CONTEXT.md D-01; Claude's Discretion on column ratio |
