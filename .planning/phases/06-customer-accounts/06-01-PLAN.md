<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Server Action `register()` | `orderToken` arrives from an untrusted URL query param (via a hidden form field) |
| client → query layer | `orderId`/`userId` reach `getOrderForUser`/`listOrdersForUser`; `userId` MUST originate only from `verifySession()`, never the request |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Information Disclosure | `getOrderForUser` (IDOR — guessing another customer's order id) | mitigate | Ownership filter lives IN the SQL WHERE: `and(eq(orders.id, orderId), eq(orders.userId, userId))`; returns `null` for both not-found and not-owned (Plan 02 renders an identical 404 for both). ASVS V4 object-level authorization. Verified by the "IDOR" + "nonexistent" tests. |
| T-06-02 | Tampering / Elevation | `register()` guest-order claim (submitting someone else's `guestToken` to steal their order) | mitigate | Guarded `UPDATE ... WHERE guestToken = ? AND userId IS NULL` — an order already claimed by its real owner cannot be reassigned; `guestToken` is 64-char crypto-random (Phase 4) so guessing is infeasible, and the `userId IS NULL` guard is the actual defense even if a token leaked. Verified by the "does not reassign" test. |
| T-06-03 | Tampering | cross-user data bleed from caching `userId` across requests | mitigate | `userId` is passed fresh from the same `verifySession()` call guarding the request (never module-cached); queries take `userId` as an explicit argument, never read it themselves (RESEARCH Pitfall 5). |
| T-06-04 | Denial of Service | best-effort claim throwing and 500-ing an otherwise-successful signup | mitigate | Claim wrapped in try/catch that logs and never rethrows, mirroring the existing verification-email best-effort block; a 0-row UPDATE is silent success (D-06). Verified by the "invalid orderToken still succeeds" test. |
</threat_model>
