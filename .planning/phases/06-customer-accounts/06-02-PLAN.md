<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → `/account/orders/[id]` | `id` route param is attacker-controllable; MUST only be used as an equality key in a session-scoped query |
| proxy.ts → Server Component | proxy redirect is layer-1 defense-in-depth only; it cannot protect Server Components (CLAUDE.md) — the page MUST re-verify |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-05 | Information Disclosure | `/account/orders/[id]` (IDOR — guessing another customer's order id) | mitigate | Page loads via `getOrderForUser(session.id, id)` (ownership scoped in SQL, Plan 01); on `null` it renders one styled "Order not found" card — IDENTICAL for missing and not-owned, so no existence leak. Never calls `notFound()` (which would still be a 404 but the styled card keeps a single code path). ASVS V4. |
| T-06-06 | Spoofing / Elevation | all three `/account/*` pages (accessing account data without a session) | mitigate | Each page calls `verifySession()` as the first statement inside its Suspense-wrapped content (layer 2, authoritative); `proxy.ts` `/account/*` redirect is layer-1 defense-in-depth (SC3 dual-auth). `verifySession()` redirects to `/account/login` when there is no session. |
| T-06-07 | Tampering | cross-user data bleed from a cached session id | mitigate | `session.id` is read fresh per request from `verifySession()` and passed straight into the query call in the same async scope — no module-level caching (RESEARCH Pitfall 5). |
| T-06-08 | Information Disclosure | order-detail rendering a recomputed/mutable total instead of the purchase snapshot | mitigate | Detail renders `order.totalKobo`/`order.items[*].lineTotalKobo` straight from the `order`/`order_item` snapshot via `OrderSummaryLines` — never recomputed (SC2/D-03). |
</threat_model>
