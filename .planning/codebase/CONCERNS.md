# Codebase Concerns

**Analysis Date:** 2026-06-05

## Tech Debt

**Unmodified Boilerplate:**
- Issue: The project is a verbatim `create-next-app` scaffold. No application code, routes, components, services, or data layers have been implemented. `src/app/page.tsx` still renders the default Next.js welcome page with links to Vercel templates and Next.js docs.
- Files: `src/app/page.tsx`, `src/app/layout.tsx`
- Impact: The project has no functionality. Any production use would require building the application from scratch.
- Fix approach: Replace `src/app/page.tsx` with actual application UI; update `src/app/layout.tsx` metadata; add required routes, components, and services.

**Placeholder Metadata:**
- Issue: `layout.tsx` still carries the default `create-next-app` metadata: `title: "Create Next App"` and `description: "Generated by create next app"`.
- Files: `src/app/layout.tsx` (lines 16–17)
- Impact: Incorrect page title and description in browser tabs, search engine results, and social sharing previews.
- Fix approach: Update `metadata.title` and `metadata.description` to match the actual application name and purpose before any deployment.

**Empty next.config.ts:**
- Issue: `next.config.ts` contains only a comment placeholder (`/* config options here */`) and exports an empty config object. No security headers, image remote patterns, redirects, or environment variable validation are configured.
- Files: `next.config.ts`
- Impact: Missing security hardening (CSP, HSTS, X-Frame-Options) and no image domain allowlisting, which will block `next/image` usage for any remote image sources added later.
- Fix approach: Add `headers()` for security headers, configure `images.remotePatterns` as needed, and add environment variable schema validation (e.g., via `zod` at startup).

## Security Considerations

**No Security Headers:**
- Risk: The application serves no HTTP security headers (Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy). This is an OWASP Top 10 misconfiguration risk.
- Files: `next.config.ts`
- Current mitigation: None.
- Recommendations: Add a `headers()` export to `next.config.ts` defining CSP, HSTS, and standard defensive headers before any public deployment.

**Known Vulnerability — PostCSS XSS (moderate):**
- Risk: The PostCSS version bundled inside `next@16.2.7` (`node_modules/next/node_modules/postcss`) is below 8.5.10 and is affected by GHSA-qx2v-qp2m-jg93 (XSS via unescaped `</style>` in CSS stringify output).
- Files: `node_modules/next/node_modules/postcss` (transitive dependency)
- Current mitigation: None. `npm audit` reports 2 moderate severity vulnerabilities.
- Recommendations: Upgrade to a patched Next.js release once one is available that resolves the inner PostCSS version. The suggested `npm audit fix --force` would downgrade Next.js to 9.3.3, which is a breaking change — avoid that path.

**No Environment Variable Validation:**
- Risk: There is no `.env` file, no `.env.example`, and no runtime validation of environment variables. When configuration is added it will be easy to deploy with missing or malformed values and receive obscure runtime errors rather than a clear startup failure.
- Files: Not yet present — risk is in the absence of any configuration layer.
- Current mitigation: None.
- Recommendations: Create `.env.example` listing all required variables as placeholder values; add a startup validation step (e.g., `zod`-parsed schema in `src/lib/env.ts`) that throws on missing required vars.

## Performance Bottlenecks

**Google Fonts Network Dependency at Render:**
- Problem: `layout.tsx` loads Geist and Geist Mono via `next/font/google`, which fetches font files from Google's CDN at build time. If the build environment has no internet access or Google Fonts is slow/unavailable, the build will fail or stall.
- Files: `src/app/layout.tsx` (lines 5–12)
- Cause: `next/font/google` performs network requests during `next build`.
- Improvement path: Switch to `next/font/local` and bundle the Geist font files directly in the repository, or add `next/font` fallback configuration.

**CSS Font-Family Inconsistency — Potential Flash of Unstyled Text:**
- Problem: `globals.css` hardcodes `font-family: Arial, Helvetica, sans-serif` on `body` (line 25), overriding the CSS variable `--font-sans` set by `next/font/google`. The CSS variable is defined in `@theme inline` but never applied to `body`, so the loaded Geist font is never actually used at runtime.
- Files: `src/app/globals.css` (line 25)
- Cause: Likely a copy-paste conflict between Tailwind v4 `@theme` approach and a manually added `body` rule.
- Improvement path: Remove the hardcoded `font-family` from `body` in `globals.css` and rely on the Tailwind `font-sans` utility class (which maps to `--font-sans`) applied on the `<html>` or `<body>` element.

## Fragile Areas

**Node.js Version Mismatch:**
- Files: `package.json` (implicit via `next@16.2.7` engine requirement), local environment
- Why fragile: `next@16.2.7` declares `engines: { node: ">=20.9.0" }` but the local Node.js installation is `v18.17.0`. The project may run in development due to npm not enforcing engine requirements by default, but CI/CD pipelines or production environments that enforce engine constraints will fail. Behaviour differences between Node 18 and Node 20+ (e.g., native fetch, crypto module changes) may cause subtle bugs.
- Safe modification: Install Node.js >=20.9.0 (LTS). Add an `.nvmrc` or `.node-version` file pinning the required version. Add `engines` to `package.json` to surface the requirement explicitly.
- Test coverage: No tests exist to catch runtime incompatibilities.
